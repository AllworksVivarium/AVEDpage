## 2. 个人主页：小游戏最高纪录

### 页面要求

1. 显示“最高单局奖金”，覆盖刮刮乐、老虎机（抑制矩阵）、共享速降、异常竞速和牌桌。
2. 下方可显示各玩法最高奖金，暂无结果时显示“暂无纪录”。
3. 总纪录显示玩法和发生时间；时间继续使用玩家端现有相对日期组件。
4. 标明奖金包含返还本金，避免把总返还误当成盈利。证券交易不计入小游戏纪录。
5. 历史游戏已由服务端回填；打开页面无需扫描全部游戏记录。

### 数据接口

`GET /api/profile` 和 `GET /api/player/state` 都新增 `gameRecords`：

```json
{
  "gameRecords": {
    "highest": {
      "game": "scratch",
      "ticketId": 123,
      "cost": 1000,
      "prize": 30000,
      "createdAt": "2026-11-06 12:00:00"
    },
    "byGame": [
      {"game":"scratch","ticketId":123,"cost":1000,"prize":30000,"createdAt":"2026-11-06 12:00:00"}
    ]
  }
}
```

没有纪录时 `highest` 为 `null`、`byGame` 为 `[]`。`byGame` 按奖金降序排列。小游戏结束后使个人资料缓存失效，再次打开个人主页时刷新 `/api/profile`。

## 3. 本人专属破纪录礼花

### 触发数据

以下现有结算响应新增 `gameHighlight`，没有事件时为 `null`：

| 接口 | 接入位置 |
|---|---|
| `POST /api/player/games/scratch` | 购票响应先暂存，玩家刮开全部格子后再处理 |
| `POST /api/player/games/slot` | 实际转轮结果展示完成后 |
| `POST /api/player/games/derby` | 旧的单人竞速结算展示完成后（若该入口仍保留） |
| `GET /api/player/games/derby/current` 与 `/stream` | 当前共享场次结算时 |
| `POST /api/player/games/derby/bet` | 同一共享场次响应可能重复携带事件，必须去重 |
| `GET /api/player/games/sky/current`、`/stream` 及 `POST /start`、`/jump` | 当前架次已结算时 |
| `POST /api/player/games/cards` | 牌局 `phase === 'ended'` 时 |

共享速降完整前缀为 `/api/player/games/sky`；共享竞速完整前缀为 `/api/player/games/derby`。SSE 的事件体与对应 current 响应结构一致。

```json
{
  "gameHighlight": {
    "ticketId": 123,
    "employeeId": 7,
    "game": "scratch",
    "alias": "匿名员工-7",
    "cost": 1000,
    "prize": 30000,
    "personalBest": 1,
    "broadcast": 1,
    "createdAt": "2026-11-06 12:00:00"
  }
}
```

### 播放规则

- 仅当事件属于当前登录用户、`personalBest === 1` 且 `prize > cost` 时播放。
- `employeeId` 是数值，现有前端 `currentUser.id` 是字符串，比较时统一类型。
- 这是跨所有小游戏的最高单局奖金纪录；相同金额不算刷新纪录。
- 使用 `ticketId` 去重，按账号保存近期已处理编号。重复 SSE、重复开伞响应、刷新、网络重连都不得重复播放。
- 不播放历史回填纪录；对重连后超过约 5 分钟的旧事件也不重播。
- 礼花只在本人页面播放，世界播报组件不触发任何人的礼花。
- 先揭晓刮刮乐结果，再播放礼花，不要在购票响应到达时提前揭晓奖金。
- 建议约 4—5 秒自动收起，提供关闭按钮和 Escape 关闭，特效层不遮挡必要操作。
- 遵循现有“关闭特效”及 `prefers-reduced-motion`：保留静态新纪录提示，停用粒子动画。
- 默认示例文案：“刷新个人最高奖金！”、“¤ 30,000”、“刮刮乐 · 本局赚了 ¤ 29,000”。

## 4. 娱乐室世界喇叭

`GET /api/player/game-highlights` 返回最新最多 12 条真实高倍大奖；可选 `?game=scratch|slot|sky|derby|cards` 按玩法过滤。

```json
{
  "items": [
    {
      "ticketId":123,"game":"scratch","alias":"匿名员工-7",
      "cost":1000,"prize":30000,"broadcast":1,"createdAt":"2026-11-06 12:00:00"
    }
  ]
}
```

- 仅登录员工可读取；接口只支持 GET，前端不能提交奖金、昵称或播报消息。
- 公开播报不包含账号、用户编号或私人破纪录标记。使用 `alias`，不要自行推测实名或用户名。
- 桌面放在小游戏右侧；移动端放在游戏区域上方，使用紧凑可滚动列表，不压缩操作区。可使用一个跟随当前玩法的公共侧栏。
- 示例：“恭喜 匿名员工-7，在刮刮乐获得 ¤ 30,000 大奖”。这里展示的是奖金，不是净盈利。
- 活跃娱乐室页面约每 12 秒调阅一次即可；隐藏页面、切换离开娱乐室或未登录时停止查询。不需要为每个小游戏同时轮询。
- 同一 `ticketId` 不重复添加；无新结果时保留列表，不要反复重建 DOM。昵称必须用 `textContent` 或进行 HTML 转义。
- 播报来自现有结算时点；刮刮乐在服务端购票结算时即可能出现在公共播报中，本人的礼花仍须等待刮开结果。
- 当前播报门槛：刮刮乐的三个稀有奖级；老虎机返还至少 10 倍；速降至少 5 倍；竞速至少 8 倍。普通牌桌固定奖励不作为稀有大奖播报，但会更新个人纪录。
- 这些门槛是奖项分类，不代表所有玩法具有相同的实际中奖概率。

## 5. 结果金额的展示

统一使用服务端返回的 `cost`、`prize`，不要在前端抽奖、计算最终奖金或改账户余额。

| 情况 | 文案示例 | 表现 |
|---|---|---|
| 投入 1,000、返还 10,000 | 本局赚了 ¤ 9,000 | 突出金额 |
| 投入 1,000、返还 1,000 | 本局返还 ¤ 1,000 · 投入 ¤ 1,000 | 普通样式 |
| 投入 1,000、返还 500 | 本局返还 ¤ 500 · 投入 ¤ 1,000 | 普通样式，不使用“中奖”礼花 |
| 投入 1,000、返还 0 | 本局返还 ¤ 0 · 投入 ¤ 1,000 | 普通样式 |

不需要突出“本局净损失”，也不使用“净赚”作为主文案。当前速降、竞速原界面中的“净变动”可按此替换。维护撤班退回本金不得计为大奖或破纪录。

## 6. 刮刮乐与共享速降规则

### 刮刮乐

- 名称统一为“刮刮乐”，用票价区分六档；仍保留三种现有刮票展示玩法。
- `GET /api/player/economy` 返回 `revision`、`tiers[].cost`、`tiers[].name`、`tiers[].topPrizes`。最高奖和票价都读取接口，不要在前端写死“100 倍”。
- 购票继续提交 `tier`、`type`、`cost`、`revision`；若响应错误码是 `RULES_CHANGED`，重新读取规则并让玩家重新确认票价。
- 后台百分比返还率是包含本金的长期平均返还，不保证每张票、每个人或每一段时间能回本。
- 以下为当前固定票种编号对应的三个稀有奖级；管理员可修改票价，因此编号与奖级绑定，不要通过金额字符串猜票种。

| 票种编号 | 原始票价 | 三个稀有奖级 |
|---|---:|---|
| t1 | 1,000 | 10、20、30 倍 |
| t2 | 3,000 | 8、15、25 倍 |
| t3 | 10,000 | 6、12、20 倍 |
| t4 | 20,000 | 4、8、12 倍 |
| t5 | 50,000 | 3、5、8 倍 |
| t6 | 100,000 | 3、4、5 倍 |

以 65% 返还率为例：三个稀有奖约每 452—485、904—969、1,808—1,938 张出现一次；空票约 46%—50%，返还半额约 10%—11%。概率会随后台返还率变化，前端不应把这些参考值作为固定承诺。

### 共享速降

- 越过安全线或未及时开伞，固定损失本次全部本金、返还为 0。
- 玩家说明中的“按本班损失比例”改为“损失本次全部本金”；移除暗示可以只损失一半的文案。
- 服务端已强制执行，旧架次保存的部分损失比例也不能覆盖这一规则。

### 低保

保留现有 `POST /api/player/relief`。余额低于 10,000 时可按原条件反复领取，不增加每日次数、冷却或新货币；仍由玩家主动点击领取，前端不自动调用。

## 9. 公告发布时间与排序（本轮发布新增）

本节随公告时间与 CRT 登录入口更新一并发布；生产实际版本以交付的发布记录为准。

- 管理员发布和编辑公告时可填写 `publishedAt`。后台输入框采用北京时间，允许回填过去或设置未来时间；未来日期只是展示时间，不是预约发布，保存后仍立即可见。
- `POST /api/admin/announcements`、`PUT /api/admin/announcements/:id` 接受 `publishedAt`，格式如 `2030-11-06T18:14:12`。不带时区的值固定按北京时间解析，也支持 `Z`、`+08:00` 等明确时区。
- 创建时省略此字段使用当前时间；编辑时省略或留空则保留原发布时间。实际创建时间仍单独保存在数据库中，不会被覆盖。
- `GET /api/announcements` 的 `items` 以及 `GET /api/player/state` 的 `announcements` 均按“置顶优先 → 发布时间从新到旧 → 编号从大到小”返回。置顶内部也按发布时间倒序。
- 公告对象新增 `publishedAt`，返回标准 UTC ISO 时间。兼容旧玩家页面的 `createdAt` 同样返回这个可编辑的展示时间；玩家日期组件继续显示“今天、昨天”等相对日期。
- 当前玩家实现直接按接口返回顺序绘制公告，服务端更新后即可生效，不必为了这个功能覆盖前端文件。若你正在重做列表，请保留接口顺序；如必须本地排序，按下面的顺序处理，不要重新只按 `id` 排序。

```js
const sorted = [...items].sort((a, b) =>
  Number(b.pinned) - Number(a.pinned) ||
  Date.parse(b.publishedAt || b.createdAt) - Date.parse(a.publishedAt || a.createdAt) ||
  b.id - a.id
);
```

检查用例：置顶的旧公告必须在不置顶的新公告之前；将某条普通公告的发布时间改为更早后，它应排到较新的普通公告之后，刷新和服务重启后仍保持这个顺序。
